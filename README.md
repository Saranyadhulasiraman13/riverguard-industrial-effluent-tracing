# RiverGuard

RiverGuard is a river-monitoring prototype for reviewing sensor anomalies and organizing follow-up inspection. It detects unusual sensor readings, groups nearby anomalies into pollution events, and ranks industrial units as plausible sources for human inspection. The included datasets are synthetic and simulated; they are not real environmental measurements, facilities, or verified incident records.

## Problem

Pollution signals can require investigation across multiple monitoring stations. A sensor anomaly alone does not identify its cause. RiverGuard combines sensor analysis with the available flow, discharge-schedule, and unit-operation records to produce an explainable inspection shortlist.

## Solution

The current pipeline cleans and validates the supplied CSVs, runs a sensor-only baseline and a historical sensor anomaly detector, groups detected anomalies into events, and then evaluates industrial units against flow direction, discharge timing, operating status, and sensor timing evidence.

Source rankings are **plausible sources for inspection, not proof of causation**. A score or confidence category does not establish that an industrial unit caused an event.

## Architecture

The experiment runner follows this flow:

```text
Raw CSV data
	-> Cleaning and validation
	-> Sensor-only baseline anomaly detection
	-> Historical sensor anomaly detection
	-> Pollution event grouping
	-> Source tracing using available flow, discharge, and operation records
	-> Explainable candidate ranking
	-> Evaluation and edge-case reporting
	-> Streamlit dashboard
```

The baseline and historical detectors both analyze sensor readings only. Flow, discharge schedules, and operating records are used in the subsequent source-tracing stage; they are not features in either anomaly detector.

## Data Processing

`src/data_loader.py` loads the known raw CSV datasets without changing them. The experiment runner passes those files through `src/data_cleaning.py` and writes cleaned copies to `data/processed/` plus an audit summary to `reports/cleaning_summary.csv`.

Cleaning trims text and normalizes only configured identifiers and categories; removes duplicate rows; parses configured timestamps as UTC, standardizes their format, and removes rows with invalid or missing required timestamps; converts sensor values and station coordinates to numeric values; flags negative sensor readings as invalid; and replaces missing or invalid sensor readings with the parameter median, falling back to the overall reading median when available. Latitude and longitude are checked against their valid numeric ranges. Suspicious high IQR readings are counted in the cleaning summary but retained; they are not automatically deleted as outliers.

The cleaning summary records input/output row counts, missing values, duplicates, timestamp changes/removals, imputed numeric values, invalid values, and suspicious extremes retained. Its values describe the current run and are regenerated by the experiment.

## Baseline Detection

The baseline selects turbidity when available; otherwise it selects the most populated numeric parameter. For turbidity, it flags values above the fixed `10.0` threshold. For another selected parameter, it uses that parameter's upper IQR fence. The baseline uses sensor readings only and writes `reports/baseline_anomalies.csv`.

## Historical Detection and Event Grouping

The historical detector calculates a shifted rolling baseline for each station and parameter from up to the previous three readings, requiring at least two readings. It compares each observation with a rolling-IQR fence and a relative baseline fence; the current reading is excluded from its own baseline. Detected readings are written to `reports/anomaly_report.csv` with the expected baseline, anomaly score, severity, and reason.

Anomalies at the same station and parameter are grouped into one event when consecutive detections are no more than six hours apart. A longer gap starts a new event. Event start/end times, peak value, parameter, duration, and severity are written to `reports/pollution_events.csv`. The pipeline does not separately diagnose or report sensor outages.

## Source Tracing

For each event, source tracing examines a nearby flow snapshot (within six hours) and directed downstream station paths. It scores upstream compatibility, scheduled discharge overlap or recent completion, the latest relevant operating status, and whether flow and event timing support downstream transport. The weights and confidence thresholds are configured in `config/weights.yaml`.

The existing configured heuristic weights remain unchanged: upstream compatibility `0.30`, discharge timing `0.30`, operating status `0.20`, and sensor/flow timing relationship `0.20`. The first and fourth components use the same flow snapshot and are related signals, not statistically independent measurements; the weights are not calibrated against source ground truth. For each candidate, the report records component values, each weighted contribution, final score, score coverage, available/unavailable components, and a human-readable summary.

Missing or conflicting flow contributes zero to flow-dependent components. A missing schedule or relevant operation record contributes zero and is explicitly marked unavailable; a present record with no match is marked available with a zero score. High priority is capped at Medium when any configured score component is unavailable. Candidates remain independently ranked for inspection; ranking priority is not a probability or source identification.

Sensor anomaly details are included as event context, not as industrial-source evidence. Citizen observations and satellite/environmental observations are counted only when genuine optional data exists, validates, and associates with an event. These observation types are not assigned to individual industrial candidates because the project has no valid source-linking field or method; they therefore do not alter unit scores. Both optional genuine-data paths are currently unavailable.

## Explainability

The report preserves its existing useful ranking fields and adds evidence availability, score contributions, optional event-observation counts, and available/unavailable evidence summaries. The dashboard displays ranked candidates, overall score, component values and contributions, coverage, evidence availability, and an explanation for the selected candidate. Results are presented as **Explainable plausibility ranking for human inspection**. These records and explanations do not establish causation.

## Evidence Fusion

Source scores combine upstream compatibility, discharge timing, operating status, and a sensor/flow timing relationship. Component weights and contributions are reported separately alongside score coverage and reasons. Missing or conflicting flow contributes no flow-based support; missing schedules and operation records are marked unavailable rather than treated as matches. High priority is capped at Medium when configured evidence is incomplete. Citizen and satellite/environmental observations can appear as event context only when valid observations match an event by exact station and inclusive event time; they do not change industrial source scores. Missing evidence is shown explicitly.

## Citizen Observation Support

The existing `data/raw/citizen_observations.csv` contains simulated scenario observations, not verified citizen-science submissions. RiverGuard does not use that file as real evidence. No genuine citizen-science observation dataset is currently available in the project.

The optional ingestion path is `data/raw/citizen_science_observations.csv`. Do not populate it with sample or invented records. When genuine observations become available, use this schema:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `observation_id` | Required | Stable unique identifier for the submitted observation. |
| `observation_time` | Required | Observation timestamp; parsed and normalized to UTC. |
| `observation_type` | Required | Submitted observation category. |
| `station_id` | One location option | Existing station identifier; exact matches can be associated with events. |
| `observation_location` | One location option | Descriptive location; displayed but not geocoded or event-matched. |
| `latitude`, `longitude` | One location option as a pair | Numeric coordinates checked against latitude/longitude ranges; not used for event matching. |
| `observation_value` | Optional | Numeric observation value when the observation has a meaningful numeric measurement. |
| `observation_description` | Optional | Submitter's description of the observation. |

Provide at least one location form: `station_id`, `observation_location`, or both coordinates. Validation checks required values, timestamp parsing, duplicate IDs, numeric values, and coordinate ranges. Invalid rows are retained with validation issues rather than silently discarded; unusually high environmental observations are not removed as outliers. Valid output is sorted chronologically.

An observation is associated only when its `station_id` exactly matches an event station and its timestamp falls inclusively between that event's start and end. Descriptive locations and coordinates are not geocoded, and no time tolerance beyond the event window is inferred. An associated record is labelled a **supporting observation**, not proof of pollution or its source.

The experiment writes `reports/citizen_observations_status.csv` to record availability and validation counts. It writes `reports/citizen_observations.csv` only when the optional input file exists and can be read. The dashboard's Citizen Observations section shows the exact unavailable status when no optional dataset is present, and otherwise offers filters and event associations when the supplied fields support them.

## Satellite / Environmental Evidence Support

No genuine satellite, remote-sensing, or independent environmental-observation dataset is currently present. The sensor, flow, and citizen-observation files in this prototype are documented as synthetic; station coordinates are metadata, not satellite observations. RiverGuard creates no event matches when the optional dataset is absent.

The optional input path is `data/raw/satellite_environmental_observations.csv`. Do not populate it with invented observations. When genuine observations are available, use this proposed integration schema; source/product metadata is optional because providers expose different fields:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `observation_id` | Required, unique | Stable identifier for one observation. |
| `observation_time` | Required | Observation timestamp; parsed and normalized to UTC. |
| `measurement_name` | Required | Name of the environmental or imagery-derived indicator. |
| `measurement_value` | Required numeric | Measured or imagery-derived numeric value; unusual magnitudes are retained. |

| `observation_location` | One location option | Descriptive location; displayed but not geocoded or event-matched. |
| `latitude`, `longitude` | One location option as a pair | Numeric coordinates checked against latitude/longitude ranges; not used for event matching. |
| `measurement_unit` | Optional | Unit associated with the measurement. |
| `platform`, `product_id`, `quality_flag` | Optional | Provider/platform and quality metadata when supplied. |

Provide at least one location form: `station_id`, `observation_location`, or both coordinates. Validation flags missing required values, invalid timestamps, duplicate IDs or duplicate observation signatures, nonnumeric measurements, missing locations, and invalid coordinate pairs/ranges. Invalid rows are retained with validation issues. Observations are sorted by parsed time; input row order is not treated as evidence of time inconsistency. Extreme measurements are not automatically removed.

An event association is made only for a valid observation with an exact `station_id` match and an observation timestamp inclusively inside the event's `start_time`/`end_time`. Coordinates and descriptive locations are not geocoded, and no time tolerance is inferred. Matches are labelled **Supporting environmental evidence**; they are not proof of pollution, source identity, or causation. The experiment writes `reports/satellite_environmental_observations_status.csv` for availability and validation counts, and writes `reports/satellite_environmental_observations.csv` only when the optional input exists. The dashboard section displays the exact unavailable message when observations are absent and offers station, measurement, and date filters when data is supplied.

## Evaluation and Limitations

The available files contain no validated anomaly/event labels or confirmed responsible-source labels. Precision, recall, F1, Top-1 accuracy, Top-3 coverage, and false-attribution rate are unavailable. `reports/experiment_results.csv` contains measured counts and descriptive proxies, including flagged-reading differences and the share of events with flow-supported candidates. These do not establish accuracy or improved detection quality. Source tracing is an explainable plausibility ranking for human inspection, not source-identification accuracy. `reports/error_analysis.csv` records implemented edge cases, tested uncertainty behavior, and unavailable evidence with descriptions and statuses. Counts remain blank when no genuine observed count is available; these rows are not incident/error frequencies.

The raw datasets are synthetic scenarios. Sensor noise and gaps are not separately diagnosed as error categories or outage reports, and discharge or operation records may be missing or incomplete. Source weights are heuristic and are not calibrated against validated ground truth. This prototype provides inspection decision support only and does not perform legal or causal attribution. The simulated citizen observations are not validated ground truth or source-ranking labels; genuine optional citizen-science and satellite/environmental observations are unavailable. Stakeholder validation has not been conducted, and no cloud deployment is claimed.

## Stakeholder / User Validation

RiverGuard is designed for a **river-restoration / environmental monitoring team member** who needs to review pollution events and decide what to inspect next without reading Python code. The dashboard is designed for stakeholder use; it has **not been validated by stakeholders**. No real stakeholder evaluation, usability score, satisfaction result, or deployment result is recorded for this project.

The intended dashboard workflow is to open RiverGuard, review the current data and event summary, filter events by station, severity, source, and date, inspect grouped events and anomaly trends, review affected stations and observed river-flow links, then select an event and a ranked candidate to inspect supporting evidence and unavailable components. Rankings are inspection candidates, not proven causes. Source ground truth and validated labels are unavailable, and accuracy metrics cannot be measured. Data supplied with the project is synthetic; optional citizen-science and satellite/environmental observations are unavailable unless genuine data is provided.

The proposed validation tasks and evidence to collect are listed in `reports/stakeholder_validation_plan.csv`. Every task remains **Not yet conducted** until observed with a real target user; do not enter ratings or claim successful completion without recorded evidence.

## Installation

Use Python 3.11 or newer. From the project root, install the packages imported by the current pipeline and dashboard:

```powershell
python -m pip install -r requirements.txt
```

## Experiment

Run the experiment first to clean the raw data and regenerate the reports:

```powershell
python experiments/run_experiment.py
```

The experiment leaves raw inputs unchanged. Optional observation reports are written only when their genuine input files exist.

## Testing

Run the automated tests with:

```powershell
python -m unittest discover -s tests -v
```

## Dashboard

Start the local dashboard from the project root with:

```powershell
python -m streamlit run app.py
```

The dashboard reads generated reports from `reports/` and project datasets from `data/processed/`, falling back to `data/raw/` where available. It presents the summary, filtered events, anomaly trend and readings, station/flow information, plausible-source rankings and evidence explanations, optional-observation availability, and evaluation/data-quality limitations. No cloud deployment is configured.
