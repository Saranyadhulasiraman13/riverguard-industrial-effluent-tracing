# RiverGuard

RiverGuard is a river-monitoring prototype for reviewing sensor anomalies and organizing follow-up inspection. It detects unusual sensor readings, groups nearby anomalies into pollution events, and ranks industrial units as plausible sources for human inspection. The included datasets are synthetic and simulated; they are not real environmental measurements, facilities, or verified incident records.

## Project Overview

Pollution signals can require investigation across multiple monitoring stations. A sensor anomaly alone does not identify its cause. RiverGuard combines sensor analysis with the available flow, discharge-schedule, and unit-operation records to produce an explainable inspection shortlist.

## Solution

The current pipeline cleans and validates the supplied CSVs, runs a sensor-only baseline and a historical sensor anomaly detector, groups detected anomalies into events, and then evaluates industrial units against flow direction, discharge timing, operating status, and sensor timing evidence.

Source rankings are **plausible sources for inspection, not proof of causation**. A score or confidence category does not establish that an industrial unit caused an event.

## Architecture

The experiment runner follows this flow:

```text
Raw CSV data
	-> Cleaning and validation
	-> Sensor-only baseline anomaly detection
	-> Historical sensor anomaly detection
	-> Pollution event grouping
	-> Source tracing using available flow, discharge, and operation records
	-> Explainable candidate ranking
	-> Evaluation and edge-case reporting
	-> Streamlit dashboard
```

The baseline and historical detectors both analyze sensor readings only. Flow, discharge schedules, and operating records are used in the subsequent source-tracing stage; they are not features in either anomaly detector.

## Data Processing

`src/data_loader.py` loads the known raw CSV datasets without changing them. The experiment runner passes those files through `src/data_cleaning.py` and writes cleaned copies to `data/processed/` plus an audit summary to `reports/cleaning_summary.csv`.

Cleaning trims text and normalizes only configured identifiers and categories; removes duplicate rows; parses configured timestamps as UTC, standardizes their format, and removes rows with invalid or missing required timestamps; converts sensor values and station coordinates to numeric values; flags negative sensor readings as invalid; and replaces missing or invalid sensor readings with the parameter median, falling back to the overall reading median when available. Latitude and longitude are checked against their valid numeric ranges. Suspicious high IQR readings are counted in the cleaning summary but retained; they are not automatically deleted as outliers.

The cleaning summary records input/output row counts, missing values, duplicates, timestamp changes/removals, imputed numeric values, invalid values, and suspicious extremes retained. Its values describe the current run and are regenerated by the experiment.

## Baseline Detection

The baseline selects turbidity when available; otherwise it selects the most populated numeric parameter. For turbidity, it flags values above the fixed `10.0` threshold. For another selected parameter, it uses that parameter's upper IQR fence. The baseline uses sensor readings only and writes `reports/baseline_anomalies.csv`.

## Historical Detection and Event Grouping

The historical detector calculates a shifted rolling baseline for each station and parameter from up to the previous three readings, requiring at least two readings. It compares each observation with a rolling-IQR fence and a relative baseline fence; the current reading is excluded from its own baseline. Detected readings are written to `reports/anomaly_report.csv` with the expected baseline, anomaly score, severity, and reason.

Anomalies at the same station and parameter are grouped into one event when consecutive detections are no more than six hours apart. A longer gap starts a new event. Event start/end times, peak value, parameter, duration, and severity are written to `reports/pollution_events.csv`. The pipeline does not separately diagnose or report sensor outages.

## Source Tracing

For each event, source tracing examines a nearby flow snapshot (within six hours) and directed downstream station paths. It scores upstream compatibility, scheduled discharge overlap or recent completion, the latest relevant operating status, and whether flow and event timing support downstream transport. The weights and confidence thresholds are configured in `config/weights.yaml`.

Units are ranked from this evidence and written to `reports/source_ranking.csv`. Missing or conflicting flow reduces upstream support; a missing schedule match or operating record contributes no match. Rankings remain plausible inspection candidates, not confirmed responsible sources.

## Explainability

The source-ranking report includes the evidence component scores, total score, confidence category, rank, affected station, and a human-readable explanation. The dashboard shows the evidence for a selected event and candidate, including upstream compatibility, discharge timing, operating-event match, and sensor-timing relationship. These explanations describe the records considered by the prototype; they do not prove a causal link.

## Citizen Observation Support

The existing `data/raw/citizen_observations.csv` contains simulated scenario observations, not verified citizen-science submissions. RiverGuard does not use that file as real evidence. No genuine citizen-science observation dataset is currently available in the project.

The optional ingestion path is `data/raw/citizen_science_observations.csv`. Do not populate it with sample or invented records. When genuine observations become available, use this schema:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `observation_id` | Required | Stable unique identifier for the submitted observation. |
| `observation_time` | Required | Observation timestamp; parsed and normalized to UTC. |
| `observation_type` | Required | Submitted observation category. |
| `station_id` | One location option | Existing station identifier; exact matches can be associated with events. |
| `observation_location` | One location option | Descriptive location; displayed but not geocoded or event-matched. |
| `latitude`, `longitude` | One location option as a pair | Numeric coordinates checked against latitude/longitude ranges; not used for event matching. |
| `observation_value` | Optional | Numeric observation value when the observation has a meaningful numeric measurement. |
| `observation_description` | Optional | Submitter's description of the observation. |

Provide at least one location form: `station_id`, `observation_location`, or both coordinates. Validation checks required values, timestamp parsing, duplicate IDs, numeric values, and coordinate ranges. Invalid rows are retained with validation issues rather than silently discarded; unusually high environmental observations are not removed as outliers. Valid output is sorted chronologically.

An observation is associated only when its `station_id` exactly matches an event station and its timestamp falls inclusively between that event's start and end. Descriptive locations and coordinates are not geocoded, and no time tolerance beyond the event window is inferred. An associated record is labelled a **supporting observation**, not proof of pollution or its source.

The experiment writes `reports/citizen_observations_status.csv` to record availability and validation counts. It writes `reports/citizen_observations.csv` only when the optional input file exists and can be read. The dashboard's Citizen Observations section shows the exact unavailable status when no optional dataset is present, and otherwise offers filters and event associations when the supplied fields support them.

## Evaluation and Limitations

The available files contain no validated anomaly/event labels or confirmed responsible-source labels. Precision, recall, F1, Top-1 accuracy, Top-3 coverage, and false-attribution rate are therefore unavailable. `reports/experiment_results.csv` contains measured counts and clearly labelled proxies, including before/after flagged-reading differences and event-level source-ranking/untraceable rates. These proxies are not ground-truth accuracy measures. Edge-case checks are also included in that report; the current pipeline does not create a separate `error_analysis.csv`.

The raw datasets are synthetic scenarios. Sensor gaps are not diagnosed as a distinct outage report, and scheduled discharge or operation records may be missing or incomplete. This prototype provides inspection decision support only; it does not perform legal or causal attribution. The existing simulated citizen observations are not validated ground truth or source-ranking labels; the optional genuine-observation file is currently absent. Satellite data is not part of the current implementation.

## Installation

Use Python 3.11 or newer. From the project root, install the packages imported by the current pipeline and dashboard:

```powershell
python -m pip install pandas pyyaml plotly streamlit folium streamlit-folium
```

## Run

Run the experiment first to clean the raw data and regenerate the reports:

```powershell
python experiments/run_experiment.py
```

Run the automated tests with:

```powershell
python -m unittest discover -s tests -v
```

Launch the dashboard from the project root with:

```powershell
python -m streamlit run app.py
```

The dashboard reads generated reports from `reports/` and project datasets from `data/processed/`, falling back to `data/raw/` where available. It presents the current data summary, filtered events, anomaly trend, station/flow information, source candidates and evidence, and the evaluation/data-quality limitations.

## Generated Reports

- `reports/cleaning_summary.csv`: cleaning and validation audit.
- `reports/baseline_anomalies.csv`: sensor-only baseline output.
- `reports/anomaly_report.csv`: historical anomaly readings and explanations.
- `reports/pollution_events.csv`: grouped anomaly events.
- `reports/source_ranking.csv`: ranked plausible inspection candidates and evidence.
- `reports/experiment_results.csv`: measured counts, proxy metrics, ground-truth availability, and edge-case results.
- `reports/citizen_observations_status.csv`: optional observation-data availability and validation status.
- `reports/citizen_observations.csv`: validated observations and event associations, written only when optional observation data is available.
